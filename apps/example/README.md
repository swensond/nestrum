# Docker integration example

From the workspace root, run:

```bash
pnpm install --frozen-lockfile
pnpm test:integration
```

Docker must be running (or set `INTEGRATION_POSTGRES_URL` to an empty PostgreSQL database and Docker is skipped). The runner deploys PostgreSQL 17 on an ephemeral loopback port and applies generated migrations through the Nestrum CLI. It runs `nestrum db ...`, then `nestrum build`, then serves the built application with the framework's `runServe` (the same code path as `nestrum serve`) and tests real HTTP requests against it and the admin shell. Every run has a separate Compose project and artifact directory; its containers, volumes, and generated artifacts are removed on success or failure.

`Project` exposes public CRUD and admin. `Article` is admin-only. Both have their own schemas, owner scopes, managers, and archive action. Auth shares the same PostgreSQL database. Admin access follows Better Auth roles: `staff` and `admin` enter administration and only `admin` manages users (`roleBasedAdminPolicies()`). Signup cannot grant a role; create the first administrator with `nestrum auth create-admin` (below), then promote staff at `/admin/access`. The test runner creates its disposable administrator the same way.

The example adds Prisma fragments and resource/app definitions through public Nestrum interfaces. The example has no HTTP bootstrap: `nestrum.config.mjs` exports the application and the framework builds, serves, and shuts it down. All routes, OpenAPI, admin pages, widgets, and actions are generated by existing framework packages.

Prisma 8's native emitter supports one database facade per package. The application-owned sibling package `example-postgres` depends on the provider facade and owns the generated artifacts. It exports the public native runtime factory; collections are read from `orm.public`.

For a persistent development deployment, start `docker compose -p nestrum-example -f apps/example/compose.yaml up --wait`. Obtain the assigned ports with `docker compose -p nestrum-example -f apps/example/compose.yaml port postgres 5432` . Set `AUTH_SECRET` and `INTEGRATION_POSTGRES_URL` (`nestrum_integration` database). Compose's local PostgreSQL credentials are `nestrum` / `integration-only`.

Build the workspace, then generate, plan, and apply migrations (with the connection variable above and `AUTH_SECRET` exported; optionally `BASE_URL`, default `http://127.0.0.1:$PORT`, and `PORT`, default 3100):

```bash
pnpm exec nestrum db generate --config apps/example/nestrum.config.mjs
pnpm exec nestrum db migrate --plan --name initial --config apps/example/nestrum.config.mjs
pnpm exec nestrum db migrate --config apps/example/nestrum.config.mjs
pnpm exec nestrum db status --config apps/example/nestrum.config.mjs
pnpm --filter @nestrum/example build:app
pnpm --filter @nestrum/example start
```

`build:app` runs `nestrum build` (it is not named `build` so the workspace-wide `pnpm build` does not require database environment variables). `pnpm --filter @nestrum/example dev` runs `nestrum dev` instead. Contracts are emitted inside `example-postgres` (`contractDir` in `nestrum.config.mjs`), because Prisma 8 allows one database facade per package; the application reads the emitted contracts from `.nestrum/contracts/` at startup and never generates them while serving. Health and readiness are at `/__nestrum/health` and `/__nestrum/ready`.

Open `http://127.0.0.1:3100/admin`; `PORT` or `--port` changes the listener port (keep `BASE_URL` consistent, as Better Auth trusts it as the origin). After `nestrum build`, create an administrator with `NESTRUM_ADMIN_PASSWORD=... nestrum auth create-admin --email you@example.com --name You --config nestrum.config.mjs` (or omit the variable to be prompted); the database must be reachable. That administrator signs in at `/admin` and promotes users to staff at `/admin/access`. Admin 2FA is required by default: on first entry the staff user is sent to `/admin/auth/2fa/setup` to confirm their password, enroll an authenticator app and save their backup codes, and every later sign-in completes a code challenge at `/admin/auth/2fa` (Better Auth's `twoFactor` plugin; the migration adds `User.twoFactorEnabled` and the `TwoFactor` table). Admin sessions older than 12 hours must sign in again. The integration runner performs this flow with a generated TOTP; `pnpm --filter @nestrum/example e2e:admin-2fa` is an optional Playwright script for a migrated PostgreSQL identity database. SIGINT/SIGTERM stop traffic and run framework shutdown before database disconnect. Stop this deployment with `docker compose -p nestrum-example -f apps/example/compose.yaml down --volumes` when its disposable data is no longer needed.

For optional manual browser QA, run `INTEGRATION_BROWSER_QA=1 pnpm --filter @nestrum/example integration` after building. The runner pauses after native form checks and prints its local URL, disposable staff credentials, and PID. Resume with `kill -USR2 <printed-pid>` after checking the browser; the suite then finishes deletion/logout/shutdown checks and cleanup. Default integration runs never pause.

## API keys

The Project resource accepts `X-API-Key` next to browser sessions (`api: { auth: ['session', 'api-key'] }`) and its policy scopes records to the key's owner, and denies deletion to keys. Administrators create keys at `/admin/api-keys` (owner user ID from `/admin/access`, scopes such as `projects:read projects:write`); the full key is shown once, then use it with `curl -H 'X-API-Key: nes_live_…' http://127.0.0.1:3100/api/projects`. The migration adds the `ApiKey` table. `pnpm --filter @nestrum/example verify:api-keys` (needs `INTEGRATION_POSTGRES_URL` and `NESTRUM_CONTRACT_JSON` for a migrated identity database) checks hashing, expiry, revocation, rotation, and the concurrent rate-limit boundary on real PostgreSQL; the Docker integration run includes an API-key section.

## Feature flags

`src/application.mjs` declares `newDashboard` (exposed to the consumer UI) and `experimentalSearch` (server only) and stores overrides in Nestrum's `FeatureOverride` table in the application database (the migration adds it). Administrators manage them at `/admin/features`; `/__nestrum/features` serves the evaluated exposed values, which the consumer app reads with `createFeatureClient()` and shows as `newDashboard: on|off`. Try `nestrum dev --feature newDashboard=true` to flip a flag for one dev process without touching storage. `pnpm --filter @nestrum/example verify:features` (needs `INTEGRATION_POSTGRES_URL` and `NESTRUM_CONTRACT_JSON` for a migrated identity database) checks persistence, the unique key under concurrent writers, precedence, deterministic rollouts and the storage-failure fallback on real PostgreSQL; the Docker integration run and the consumer browser checks include feature-flag sections.

## Enterprise SSO

`src/application.mjs` enables `sso: { enabled: true }` on the auth definition. Administrators add OpenID Connect or SAML 2.0 providers at `/admin/auth/sso` (admin 2FA and the `sso.*` ABAC actions apply; the client secret is write-only, encrypted at rest and never shown again). The SAML detail page lists the ACS URL and SP entity ID to enter in the identity provider. Users sign in with `POST /api/auth/sign-in/sso` (by `email` domain, `providerId` or `organizationSlug`); an SSO session is tagged `authMethod: 'sso'` and never satisfies the admin second factor. The migration adds the `SsoProvider` table and two `Session` columns. `pnpm --filter @nestrum/example verify:sso` (needs `INTEGRATION_POSTGRES_URL` and `NESTRUM_CONTRACT_JSON` for a migrated identity database) checks encryption at rest, concurrent creation, a full OIDC sign-in, disabling and deletion on real PostgreSQL, and `pnpm --filter @nestrum/example e2e:sso` (same variables plus Playwright) drives the admin lifecycle for both protocols in a real browser.
