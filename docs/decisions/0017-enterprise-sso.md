# 0017 — Enterprise SSO on Better Auth's SSO plugin

## Status

Accepted — completes [Post-MVP Plan 06](../post-mvp/sso/README.md).

## Context

Enterprises sign in through their own identity provider. Nestrum needs OpenID Connect and SAML 2.0 without handing applications protocol handlers, provider CRUD, secret handling or a management UI, and it must not let an external claim or an upstream login weaken admin 2FA or ABAC.

## Decision

- **Responsibility.** Better Auth's official `@better-auth/sso` plugin (1.7.6, pinned with the other Better Auth packages) owns protocol correctness: OIDC discovery, authorization and token flow, JWKS and ID-token validation, SAML assertion validation, NameID identity, callbacks and account finalization. Nestrum owns the provider registry, secret persistence, enable/disable, organization and domain mapping, provisioning policy, diagnostics, audit events, the admin API and the admin UI.
- **Enabling.** `defineAuth({ sso: { enabled: true } })`. Off by default; when off, no SSO route, service or admin page exists and `application.auth.sso` is `undefined`. Unknown SSO options throw.
- **Storage.** The plugin's own provider table joins the framework-owned auth contract as `SsoProvider` (PostgreSQL and MongoDB), with no second provider database. Nestrum's provider state uses the plugin's supported `additionalFields` on that table: `displayName`, `enabled`, `createdBy`, `updatedBy`, `lastValidatedAt`, `lastValidationStatus`, `lastSuccessfulLoginAt`, `createdAt`, `updatedAt`. `Session` gains nullable `authMethod` and `ssoProviderId`, set only inside the SSO callbacks and never from client input. The contract-parity test compares every model with Better Auth's own schema. Existing applications migrate one additive table and two additive columns.
- **Registry.** `application.auth.sso` (`SsoProviders` in `@nestrum/core`) is the only writer. The plugin's registration endpoint is disabled (`providersLimit: 0`) and none of its management endpoints are forwarded over HTTP, so there is exactly one path to change a provider. Provider IDs are 3–48 characters of lowercase letters, digits and hyphens, unique, permanent, and never a reserved Better Auth or common social ID; display names can change, IDs cannot. Domains are normalized DNS names; several providers may share a domain or an organization.
- **Secrets.** OIDC client secrets and SAML private keys are sealed with AES-256-GCM before they reach the database (`nsso1:<iv>.<ciphertext>`), with a key derived by HKDF from the auth secret, so no second secret is configured. Sealing happens in the auth database adapter, so the plugin reads plaintext while the table never stores it. Admin responses carry `clientSecretConfigured: true`, never the value; an edit keeps the stored secret unless a replacement is supplied. Changing the auth secret makes stored provider secrets unreadable (`SSO_SECRET_UNREADABLE`) until they are re-entered.
- **Outbound safety.** An IdP URL must be HTTPS on a public host (resolved, so a public name pointing at a private address is refused), unless its origin is declared in `sso.trustedIdpOrigins` for private or loopback networks. Origins of enabled providers are then added to Better Auth's dynamic trusted origins, which the plugin requires before it will fetch them; browser origin checks in `handle` stay on the static list.
- **Routes.** Through `/api/auth`, only these SSO paths are reachable: `POST /sign-in/sso`, `GET /sso/discover`, `GET /sso/callback/:providerId`, `GET|POST /sso/saml2/sp/acs/:providerId` and `GET /sso/saml2/sp/metadata`. Sign-in resolves the provider itself (enabled providers only) and forwards an allowlisted body, dropping client scopes and extra authorization parameters; post-login targets must be same-site paths or trusted origins. Callbacks and ACS posts for a disabled provider are refused with `SSO_PROVIDER_DISABLED`. The ACS accepts the IdP's cross-site form post, and only that path skips the origin check.
- **Login discovery.** By email domain, `domain`, `providerId` or `organizationSlug` (through an application-supplied `resolveOrganization`). No match is `404`; several matches are `409 SSO_DISCOVERY_AMBIGUOUS` with a choice list, never an arbitrary pick. With domain verification on, only verified domains route sign-in.
- **Domain verification.** Opt-in (`sso.domainVerification.enabled`). Then the plugin's own rules apply: sign-in and linking require a verified domain. The admin requests a DNS TXT record (`_nestrum-sso-<providerId>.<domain>`), then verifies it; changing domains resets trust. Status is `verified`, `pending`, `unverified` or `not-required`.
- **Validation.** `test` is configuration validation: OIDC discovery with issuer check and required endpoints; SAML metadata parsing, IdP entity ID, certificate structure and expiry. Results carry fixed diagnostic messages (never remote bodies) and are stored as last-validation time and status. Enabling a provider, and creating or editing an enabled one, validates first. A passing test is never reported as a login.
- **SAML.** Preferred setup is IdP metadata XML; manual SSO URL plus certificate is the fallback. The SP entity ID, ACS URL, metadata URL and callback are derived and shown. SP-initiated login uses the plugin's InResponseTo tracking. IdP-initiated login is refused unless the operator sets `sso.saml.allowIdpInitiated` and the provider configures an `idpInitiatedCallbackUrl`, and it still passes the plugin's response validation; unsolicited responses are recognized conservatively before the plugin runs.
- **Admin.** `GET|POST /__admin/auth/sso`, `GET|PATCH|DELETE /__admin/auth/sso/:providerId`, `POST …/test|enable|disable`, `POST …/domain-verification[/verify]` and `GET …/capabilities`, plus the `/admin/auth/sso`, `/new` and `/[providerId]` pages. They sit behind the complete admin boundary (same origin, session, `admin.access`, 2FA) and then need the `sso` ABAC actions `read`, `create`, `update`, `delete`, `enable`, `disable` and `test` (domain verification needs `update`), granted to `admin` by `roleBasedAdminPolicies()`; a missing policy denies. Responses are `no-store`.
- **Audit seam.** `sso.onAudit` receives `created`, `updated`, `enabled`, `disabled`, `deleted`, `test-attempted` and `domain-verification-changed` with provider ID, protocol, organization, actor and the names (never values) of changed settings. Failures never fail the operation. Full audit history is out of scope.
- **Delete.** Removes the provider row and its pending verification record only. Users, their linked `Account` rows and sessions remain; those accounts simply can no longer sign in through that provider.
- **Provisioning.** `sso.provisioning` passes Better Auth's `disableImplicitSignUp`, `provisionUser`, `provisionUserOnEveryLogin`, `organizationProvisioning`, `resolveUser` and `trustEmailVerified` through unchanged. New users get the ordinary `user` role. `resolveUser` is wired but the plugin runs it inside a native database transaction, which Nestrum's Prisma adapter does not provide, so it currently fails closed (`SSO_USER_RESOLUTION_REQUIRES_NATIVE_TRANSACTIONS`, no user or session created).
- **Subject and 2FA.** The default SubjectFactory adds `authMethod: 'sso'` and `ssoProviderId` to the subject of an SSO session; custom mappers receive the same session fields. An SSO login never satisfies admin 2FA: `sessionAssurance` returns `challenge-required` (or `setup-required` when not enrolled) for any session whose `authMethod` is `sso`, so an administrator must also sign in with their password and TOTP code. Upstream MFA claims (`acr`, `amr`, `AuthnContext`) are not trusted. IdP attributes map to profile data only through explicit mapping and never to `role`.

## Consequences

- SSO-only administrators cannot yet complete the second factor, because enrollment and the challenge are password-based. They can reach staff/admin functions only after the framework gains a non-password assurance path.
- `organizationId` is an application-owned identifier. Nestrum does not install Better Auth's organization plugin, so organization membership provisioning and automatic assignment by domain are not active; `organizationProvisioning` is passed through for applications that add that plugin themselves.
- Changing the auth secret invalidates stored provider secrets.
- Single logout, `private_key_jwt`, OAuth2-only providers, per-provider rate limits and an audit-history product are future work.
