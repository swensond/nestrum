# Extension contribution seams

Extensions are explicitly installed, application-owned contributions with named owners. Phase 14 uses the existing app graph and registries; it does not introduce package discovery, a plugin loader, or a shared mutable plugin registry.

| Contribution | Available seam | Ownership and conflict rules |
| --- | --- | --- |
| Apps | `defineApp`, `defineApplication({ apps })`, `dependsOn` | Installation is explicit. Duplicate names, unknown dependencies, and cycles fail; configure/ready follow dependency order and shutdown reverses it. |
| Resources and policies | App/application `resources` and `policies` arrays | App-owned definitions use canonical database/model identities. Duplicate registrations fail; schemas/backends resolve before configure hooks. Admin registration remains an explicit independent opt-in. |
| DI providers | `createRuntimeContainer(application)` and runtime `di.container/createScope` | Applications register typed providers on their supplied InferDI root. Request scopes isolate lifetimes; a supplied root stays application-owned. App hooks may coordinate setup/cleanup but do not gain an implicit provider-discovery API. |
| Admin configuration | `admin.register(Resource, { listDisplay, fields, actions })` | One registration owns the resource's admin configuration. Duplicate fields/actions are not merged across plugins. Known action names and readonly restrictions validate before traffic. Handler functions stay server-side. |
| Admin components | Explicit `AdminComponentRegistry.register(name, component)` | App entry modules import contributors in a deliberate order, then seal one registry before serving. Names are unique across contributors; collisions fail instead of silently replacing components. SSR/client share the same compiled entry. |
| CLI commands | Phase 15 implements built-in `db generate/migrate/status`; generic contributed commands remain designed | Future descriptors should carry owner, unique command path, validated arguments, and an awaited application-context handler. Reserve existing framework command paths and reject collisions before execution. No automatic package scanning or shell-string dispatch. |
| Database extensions | Phase 15 `PrismaProviderExtension` source/control modules plus existing app fragments/named definitions | Descriptors retain owner/name/database/provider, validate mismatches/duplicates before invocation, and preserve provenance/native validation. Config modules reach offline and online workflows. Advanced options remain contributor/provider-owned; client setup/disposal stays distinct from generation. |

An app distributes its resource/policy/fragment definitions and, when needed, a separate browser-safe admin component entry. The application composes both explicitly. A dependency on an app does not install its frontend modules or expose its resources publicly. The build entry may import another app's widget-registration function, passing the same registry, then seal after all contributions. Registration order is deliberate, and conflicts always fail.

The composition sequence is: resolve installed app dependencies; snapshot resource/policy/database definitions; assemble and validate contracts; resolve metadata and schemas before configure hooks; configure services; finish ready hooks before traffic. Frontend registration happens during shell compilation/module initialization and cannot mutate server configuration on a request. Shutdown drains requests before reverse app cleanup and owned DI disposal.

Future CLI/database descriptors should follow the same explicit ownership, validation, conflict, and lifecycle rules instead of creating a second app graph. Command handlers must not leave partially started apps or undisposed clients on error. Provider-specific options must remain within provider modules, preserve canonical metadata, and reject unsupported combinations; compression, partitioning, physical indexes, and related advanced storage implementations remain [post-MVP](post-mvp.md).

Generic contributed CLI command descriptors remain design constraints. Phase 15 exports database extension descriptors and concrete database commands/lifecycle integration; [database workflow](database-workflow.md) documents usage. Phase 16 proves live providers. Custom pages, dashboards, bulk actions, discovery, plugin installation/version negotiation, and runtime component loading remain excluded.
